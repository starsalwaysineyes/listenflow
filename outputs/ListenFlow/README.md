# 听流 · ListenFlow

macOS 原生实时转写、全文整理与上下文问答工具。默认用火山引擎豆包流式语音识别（云端），可在设置里切回本地 Qwen3-ASR 1.7B；问答与整理用 DeepSeek Flash。

## 打开与使用

当前源码版本为 0.10.0。若旧版正在录音，先完成录音、暂停并退出旧版，再打开新版。第一次使用先在「模型与 API 设置」里填豆包语音的 API Key（见下文「识别引擎」）；左下角显示「豆包云端识别已就绪」即可开始。已保存的旧会话可以直接从「历史记录」中打开。

1. 在左侧「音频来源」三选一：
   - **全局**（默认）：电脑上所有 App 的声音和麦克风一起录，不用选 App，适合线上会议——对方的话和你自己的话都有。电脑上的声音标为「电脑声音」，你说的话标为「麦克风」。听流自己发出的声音不录。首次需要授权「屏幕与系统音频录制」和「麦克风」；麦克风没授权或没有输入设备时，会话照常进行，只转写电脑上的声音，并提示原因。
   - **指定 App**：先在目标 App（腾讯会议、浏览器、播放器）里播放声音，再在列表里选中它。首次需要在 macOS「系统设置 → 隐私与安全性 → 屏幕与系统音频录制」中授权听流，必要时重启应用。
   - **我的麦克风**：线下课堂和线下会议的用法。不需要选中任何 App，也不创建屏幕采集流；点击「开始转写」即可。
2. 点击「开始转写」。
   - 豆包引擎：开始说话后不到 1 秒出现灰色的实时预览，会随着说话不断修正；一句说完（停顿约 1 秒）后换成定稿的一行。一直不停顿时，服务端大约每 20 秒定稿一次。
   - 本地模型：在讲话的停顿处切段识别，一般 3–8 秒出一段；一直不停顿时最长 8 秒，在最安静的位置切开。一句话不足 3 秒时，要停顿约 1.5 秒才单独出字，避免把讲课时的短句切成碎片。
3. 全局模式下麦克风默认打开，指定 App 模式下默认关闭；两种模式录音中都可以用「同时录麦克风」开关随时开关（开着会额外录入会场声音）。关闭前已采到的最后一小段仍会完成识别。用扬声器外放时，麦克风会把 App 的声音再录一遍；这类句子会自动去掉，见下文「外放回声」。
4. 在右侧提问，或点击总结、待办等快捷问题。回答使用点击提问时的转写快照，转写继续运行。
5. 暂停后可以新建会话、打开历史记录，或导出 Markdown。退出前先暂停，并等待当前音频识别完成。豆包引擎下暂停时，正在说的半句会在约半秒内定稿，不会丢。

随时可用：菜单栏图标常驻，本身就是录制状态指示。关掉主窗口不会退出应用，录音继续。

### 开会、上课时怎么用

- **线下课堂 / 线下会议**：来源选「我的麦克风」，`⌥⌘R` 开始。中途想记下板书，`⌥⌘S` 拉框截图，`⌘K` 直接提问。
- **腾讯会议 / 网课**：用默认的「全局」直接开始。只想听某一个 App、不想让提示音和别的窗口的视频混进来时，选「指定 App」。

## 识别引擎

设置 →「语音识别」→「识别引擎」。切换前先暂停转写。

| | 豆包（云端，默认） | 本地模型 |
| --- | --- | --- |
| 音频去向 | **发送到火山引擎**；只在有人说话时发送 | 不离开这台 Mac |
| 出字 | 开始说话约 0.8 秒出预览，句末约 0.5 秒定稿 | 一般 3–8 秒一段 |
| 断句、标点、数字 | 服务端完成，自带二遍识别 | 本机按停顿切段 |
| 需要 | 网络、API Key、账户额度 | Python 环境与约 2.7 GB 内存 |
| 识别档位、合并重识别 | 不适用，设置里不显示 | 可用 |
| 会后「精修全文」 | 把暂存的录音上传到豆包录音文件识别，另外计费 | 在本机按 30 秒一段重识别 |
| 外放回声过滤、人名术语、整理、问答、导出 | 相同 | 相同 |

**豆包的配置**

- API Key：火山引擎控制台「豆包语音」的密钥，流式识别和录音文件识别共用。保存在 `~/.listenflow/keys.json` 的 `volcengine-asr` 一项（见下文「数据」）。
- 资源 ID：默认 `volc.seedasr.sauc.duration`（2.0 小时版，按送入的音频时长计费）。并发版是 `volc.seedasr.sauc.concurrent`，需要单独开通。资源没开通时握手可能照样成功，要到开始识别才报错；报错会带上服务端给的原因。
- 人名、术语会作为热词随连接发送（服务端上限约 100 个 token，超出的部分不发送）。

**它是怎么送音频的**

- 每个音频来源（指定 App、麦克风）各开一条连接，互不影响。
- 小时版按送入的音频计费，而且连接上约 8 秒收不到音频就会被服务端断开。所以听流不传静音：检测到有人说话才建立连接（并补上开口前 0.6 秒），连续安静 3 秒后发结束包关闭，下次开口再连。安静的课间、会议里没人说话的时间不计费。说话检测用的是和本地切段相同的办法（200 Hz 以上的能量对比滚动底噪）。
- 句子定稿前，对应的音频一直留在内存里。连接中途断开时自动重连（间隔从 0.4 秒起，最长 3 秒一次），连上后把还没定稿的音频重新发一遍，所以不丢字；连续约 2 分钟都连不上才停止转写并提示，已识别的内容保留。密钥无效、资源未开通、额度不足这类重试也没用的错误会立刻停止。
- 麦克风和指定 App 同时录时，麦克风这一路的判停时间改为 0.2 秒，分句更短。原因见 TESTING.md 0.8.0：按 1 秒判停时，外放回声会和你紧接着说的话连成一句，服务端定稿时只留下回声。

切到豆包后本地模型进程会退出，释放内存；切回本地时重新加载。

**会后精修（豆包录音文件识别）**

实时识别是边听边出字，一句话讲满约 20 秒会被服务端强制定稿，切点可能落在词中间。录音文件识别拿到的是整段音频，能结合前后文，分句也按语义来，实测更准（数据见 TESTING.md 0.9.0）。

- 设置里开启「暂存录音」（默认开启）后，发给豆包的那部分音频——也就是有人说话的片段——同时保存在本机 `~/.listenflow/audio/<会话>/`。静音本来就不上传，也不保存。
- 会后在「原始转写」右上角点「精修全文」：暂存的录音按约 5 分钟一段上传（两段同时进行），返回的分句替换原来的实时结果，时间戳对应回录音时的实际时间。一段讲话超过 5 分钟没有停顿时，在段尾 20 秒内最安静的地方切开。
- 资源 ID 默认 `volc.seedasr.auc`，在设置里可改；密钥和流式识别是同一个。按音频时长另外计费，也就是同一段音频实时一次、精修一次。
- 全部完成后删除暂存录音。中途失败或点了「停止」：已完成的段保留，录音还在，再点一次只上传没做完的段。
- 某一段返回的文字比实时结果少一半以上（或是空的）时，这一段保留原文不替换。
- 麦克风和指定 App 同录时，麦克风的录音里有外放回声。这一路上传时改为按 0.3 秒静音分句，返回后再过一遍回声过滤，和实时那一遍的做法一致。
- 关掉「暂存录音」就不保存任何音频，也就没有「精修全文」。

## 给 agent 用的命令行：lstf

`lstf` 让 Claude Code、Codex 这类能跑命令的 agent 读到听流的转写：正在录的这一场，或者历史上的任何一场。对 agent 说「`lstf --help` 查一下刚才会上定的截止时间」，它读完帮助就知道该怎么取。

```sh
lstf status                       # 听流是否在运行、是否在录、当前是哪一场
lstf read --minutes 5             # 当前这场最近 5 分钟
lstf read                         # 当前这场，从第 1 行起，最多 200 行
lstf read 3F2A91BC --offset 201 --limit 100   # 像读文件一样：起始行号 + 行数
lstf read --tail 30               # 最后 30 行
lstf read 3F2A91BC --organized    # 整理稿
lstf list                         # 历史会话，新的在前
lstf search 预算                  # 哪场会的哪一句提到过
lstf refine 3F2A91BC --wait       # 对还没精修的会话启动精修，等它完成
```

- **只读**。不能开始、暂停录制，不能新建或修改会话。唯一的例外是 `refine`：对有暂存录音、还没精修的会话启动「精修全文」。
- **只有定稿的句子**。每句定稿后听流立即存盘，`lstf` 直接读会话文件，所以正在录的内容一般在说完约 1 秒后就能读到；灰色的未定稿预览不在其中。一直不停顿的讲话，豆包约 20 秒才定稿一行。
- **会话怎么指定**：省略或 `current` 是听流里当前打开的那一场，`latest` 是最近一场，其余用 `lstf list` 第一列的 ID（写开头几位即可）。
- **分页**：每行是一句话，带行号、从会话开始算起的时间和来源。输出末尾写明共多少行、接着读该用哪个 `--offset`；正在录制的会话下次从上次读到的行号之后接着读。
- **精修由听流 app 执行**，所以听流必须在运行；正在录制的会话要先暂停。不是当前打开的那一场也可以，听流在后台完成，不切换界面（这种情况只支持豆包引擎录的会话）。豆包引擎下精修按音频时长另外计费。精修会重新断句，行号整体变化。
- `status`、`list`、`read`、`search` 加 `--json` 得到结构化输出。退出码：0 成功，1 做不到（原因在标准错误），2 命令写错了。
- **安装**：从源码 `./build.sh` 时，如果存在 `~/.local/bin`，会自动把它链接成 `~/.local/bin/lstf`。用发布包的话手动链接一次：`ln -s /Applications/ListenFlow.app/Contents/MacOS/lstf ~/.local/bin/lstf`（或 PATH 里的其他目录）。
- 听流没开时也能读历史和搜索；`status` 会说明它没有在运行。

需要知道：agent 读到的会议内容会发给它背后的模型服务。`lstf` 本身不联网，也没有扩大本机的暴露面，会话文件本来就只有你自己能读。

## 识别档位与事后精修（本地模型）

以下内容只在识别引擎为「本地模型」时有效。豆包引擎自带二遍识别，没有档位；它的「精修全文」走的是录音文件识别，见上一节。

设置 →「识别档位」：

| 档位 | 做法 | 适合 |
| --- | --- | --- |
| 自动（默认） | 接电源时用高精度，用电池或开启低电量模式时省电 | 大多数情况 |
| 省电 | 每段只识别一遍 | 没接电源的长时间课堂 |
| 高精度 | 先实时出字；同一来源每攒满约 14–20 秒，合起来重新识别并替换这几行 | 接着电源的线上会议 |

高精度档录音时，原始转写里会有一条淡虚线：线上方是已经合并重识别、不会再变的文字；线下方是刚出的实时短片段，稍后会被合并替换。

侧栏左下会显示当前实际生效的档位，例如「识别：高精度 · 自动（接电源）」。

**事后精修**：设置里开启「暂存录音」（默认开启）后，录音时会在本机保存 16 kHz 单声道音频。会后在「原始转写」右上角点「精修全文」，按约 30 秒一段重新识别整场；完成后自动删除暂存音频。最适合用电池、以省电档录完的会议。精修过的会话如果已有整理稿，下次「更新整理稿」会按新原文整篇重整。

实测（2224 字中文语音，带底噪，经真实 app 流程回放）：

| | 底噪 | 快语速几乎无停顿 |
| --- | --- | --- |
| 0.5 版 4 秒硬切（离线实验） | 121 错 | 127 错 |
| 省电 | 72 | 90 |
| 高精度 | 58 | 59 |
| 省电 → 事后精修 | 67 | 60 |

识别本身很快（实时率约 0.05），省电约占 7.5% 的 GPU 时间，高精度约 13%。重新识别只在没有实时片段等待时进行，不会拖慢出字。合并后的一行会覆盖较长时间段，所以这几段的时间戳更粗。

## 外放回声

开会时用扬声器外放、又开着「同时录麦克风」，对方的话会从扬声器出来再被麦克风录一遍。听流把麦克风识别出的每一句和同一时段 App 那一路的文字比对：大部分内容重合的就是回声，丢掉麦克风这句，只留 App 那句（App 是数字采集，更清楚）。

- 你和对方同时说话时，麦克风这句以你的话为主，重合度低，照常保留。
- 「好的」「对」这类两三个字的短句，只有和 App 那句在时间上几乎重叠才算回声。
- 麦克风的句子要等 App 同一时段识别完才能比对，开着 App 时会晚出现一点（通常不到 1 秒）。豆包引擎下 App 一句话可能持续十几秒才定稿，所以比对时也算上 App 正在显示的预览文字，最多等 4 秒。
- 豆包引擎下，麦克风的实时预览如果和 App 正在说的内容重合，会先不显示，避免回声闪一下再消失。
- 左侧麦克风开关下会显示本次已去掉几句。被去掉的句子不保存。

为什么不用系统的回声消除：macOS 的语音处理能把回声消得干干净净，但它运行时，其他 App 直接读麦克风只能拿到近乎静音。实测打开后，腾讯会议的麦克风音量指示完全不动，对方会听不到你。自己做的线性回声消除能压低 15–24 dB，模型仍能从残余里认出 85–125 / 193 字，所以改为按文字去重。

## 刘海灵动岛

转写时把鼠标移到屏幕顶部的刘海处，会向下展开一块黑色面板，显示最近的转写；移开鼠标后自动收起。点面板右上角的图钉可以固定展开，开课、开会时一直看着；菜单栏图标里也有「固定展开灵动岛」。

- 收起时什么都不显示，也不挡鼠标。设置 →「刘海灵动岛」里可以开启「收起时常亮显示最新一句」。
- 拖动灵动岛底部的小横条可以调整高度，松手后记住；默认 300 pt（高精度档长段约 4 条，省电档短片段更多）。可以向上滚动看更早的内容。设置里有「恢复默认高度」。
- 宽度在设置里用滑块调整（480–1100 pt，默认 720 pt，按 16 寸屏校准）；14 寸屏可以调窄一些。不会窄于刘海加两侧按钮，也不会超出屏幕。
- 最新一句最亮，越早越淡；虚线以下是尚未合并重识别的实时片段。
- App 声音和麦克风同时录时，每条标出来源。
- 灵动岛不会出现在屏幕共享和截图里。
- 没有刘海的屏幕上，显示在屏幕顶部正中。

## 整理稿

在记录区顶部切换到「整理稿」，点击「整理当前记录」。DeepSeek 会将碎片合并成完整句子、补标点、清理重复字和口头语，并按话题分段。保留原意、细节和时间戳，原始转写始终可查。

- **增量整理**：整理结果按批保存。除最后一批外都视为已定稿，后续整理不再重发，因此早先的措辞保持稳定。只有最后一批连同新增转写一起重做，衔接处自然形成重叠区重新顺句，不会在段落中间硬切。
- 「自动更新」默认关闭。手动开启后，有新增文字时约每 30 秒整理一次；会向已配置的问答 API 发送转写文字并产生 API 用量。
- 整理过程中继续采集音频；生成结束后会提示还有多少新片段未纳入。
- 失败或手动停止会丢弃未完成的预览，保留原文与上一版完整整理稿；失败后自动更新会关闭。
- 整理稿自动随会话保存，重新打开历史会话仍可查看。复制按钮复制当前视图；导出同时包含整理稿、原文和问答。
- 长记录会分批整理，避免因输出长度不足而悄悄变成摘要。批次边界仍可能需要人工调整段落。
- AI 整理不能保证纠正所有识别错误，不确定内容要求标记「听辨不清」。Ask 继续依据原始转写回答，避免把整理误差再次放大。


## 本机配置

- macOS 26.6.2 / Apple M1 Max / 64GB。
- 默认 ASR：`mlx-community/Qwen3-ASR-1.7B-8bit`，可切换 0.6B。
- Python：`/Users/aurora/Desktop/workspace/asr-realtime-lab/.venv/bin/python`。
- 复用已有 Hugging Face 缓存，启用离线模式；没有再次下载模型。
- 问答地址：`https://api.deepseek.com`；模型：`deepseek-flash`。
- DeepSeek 请求默认关闭深度思考，流式显示回答；每次回答上限 4096 tokens。
- API 密钥保存在 `~/.listenflow/keys.json`，按 API 地址各存一项。源码与设置文件没有密钥。

设置界面支持更换 `chat/completions` 兼容服务、模型和密钥。API 地址需使用 HTTPS，本机服务可以使用 HTTP。填入包含 `/v1` 的地址时，会保留该路径；也可直接填写完整 `/chat/completions` 地址。

## 数据

- 识别引擎为豆包时：有人说话期间，16 kHz 单声道音频经 TLS 实时发送到火山引擎（`openspeech.bytedance.com`）；静音不发送。开启「暂存录音」时，发出去的这部分音频同时保存在本机，供会后「精修全文」再上传一次（录音文件识别，同一域名）；关闭时听流不把音频写入磁盘。火山引擎一侧如何保留数据以其服务条款为准。
- 识别引擎为本地模型时：音频不离开这台 Mac。关闭「暂存录音」时，音频只在内存和本地进程管道中流转，不落盘。
- 原始音频任何情况下都不发给问答 / 整理用的 LLM。
- 开启「暂存录音」时，音频以 16 kHz 单声道保存在 `~/.listenflow/audio/<会话>/`（目录 0700、文件 0600），精修完成后删除，最长保留 7 天。本地模型存的是送去识别的每个片段（`<来源>.pcm`）；豆包引擎存的是上传过的讲话片段（`<来源>.stream.pcm`，另有一个记录每段起始时间的 `.stream.idx`）。0.8.0 及更早版本存在 `~/Library/Application Support/ListenFlow/Audio/` 的音频，新版第一次启动时会移过来。
- API 密钥保存在 `~/.listenflow/keys.json`（目录 0700、文件 0600，明文 JSON：问答接口以 API 地址为键，豆包语音以 `volcengine-asr` 为键）。可以直接用编辑器改；文件权限过宽时读取时会收紧，文件不是合法 JSON 时听流不会覆盖它。0.8.0 及更早版本把密钥存在 macOS 钥匙串（服务 `local.ListenFlow.llm`）；新版不再使用钥匙串，第一次用到某个密钥时把它从钥匙串移到这个文件，并删除钥匙串里的那一项。
- 提问时发送当前会话的全部转写文字、最近 12 条问答和本次问题到配置的 API。
- 整理时只发送当前转写快照，不使用先前问答作为原文。
- 会话文字自动保存在 `~/Library/Application Support/ListenFlow/Sessions/`，保存为 JSON。
- 同一目录下的 `state.json` 是听流运行时写的状态（是否在录、当前会话、精修进度），退出时删除；`requests/` 是 `lstf refine` 向听流发请求用的，30 秒内没人处理的请求自动清掉。两者都不含转写内容。
- 暂停录制不会关闭问答。切换会话前需要等待已有音频处理完。
- 左下状态显示当前引擎是否就绪（豆包：等待声音 / 正在连接 / 识别中 / 正在重连）；底栏标明是云端识别还是本地处理，并显示最近一句的延迟（豆包：句子说完到定稿；本地：开始采集到文字返回）。
- 积压时显示提示；队列过长会暂停采集，识别进程超时会明确报错，不会伪装实时。

## 构建

要求 Apple Silicon、macOS 15+ 和 Swift Command Line Tools。当前机器可直接运行：

```sh
./build.sh
```

需要保留正在运行的旧版时，可以指定另一个构建位置：

```sh
LISTENFLOW_APP_DIR="$PWD/../听流-整理版.app" ./build.sh
```

产物为项目目录旁的 `听流.app`。使用本地临时签名；更换构建后，macOS 可能要求重新确认录制权限。当前版本复用本机 Python 与模型缓存，还不是可以任意分发给其他电脑的独立安装包。

源码结构：

- `Sources/CaptureEngine.swift`：ScreenCaptureKit 采集全部 App 或指定 App 的音频；独立 AVAudioEngine 麦克风；转换为 16kHz 单声道。
- `Sources/AudioChunker.swift`：按滚动底噪判断停顿（只看 200 Hz 以上的能量，避开空调、风扇等低频噪声），在停顿处切段；8 秒上限时在最安静处切开。
- `Sources/VolcProtocol.swift`：豆包流式识别的帧编解码（gzip 用系统 zlib）、分句去重、未定稿音频的补发缓存、说话检测。纯逻辑，不含网络。
- `Sources/VolcStream.swift`：每个音频来源一条 WebSocket 连接（URLSession）：流式上传、实时预览与定稿、断线重连、暂停时收尾。
- `Sources/VolcFile.swift`：豆包录音文件识别。暂存录音的分段与切点、上传音频里的时间和录音时刻的对应、请求与结果解析、替换原文的把关（纯逻辑），以及提交、轮询的客户端。
- `Sources/Recognition.swift`：电源判断、音频暂存（两种引擎各自的文件）、精修窗口的分组、合理性检查与替换、外放回声过滤。
- `Sources/ASRBridge.swift` / `Backend/asr_worker.py`：本地引擎，常驻 MLX 模型、JSON lines 本地管道。
- `Sources/LLMClient.swift`：上下文快照、流式问答、错误与截断检查。
- `Sources/Storage.swift`：设置、`~/.listenflow` 下的密钥文件、会话、导出。
- `Sources/AgentBridge.swift`：app 和 `lstf` 之间交换的状态文件与请求文件，两边共用。
- `CLI/LstfCore.swift`：`lstf` 的参数解析、会话选择、分页和输出（纯逻辑）；`CLI/main.swift`：读文件、向 app 发精修请求。
- `Sources/AppModel.swift` / `ContentView.swift`：会话状态和 SwiftUI 界面。

## 当前边界

完整实测结果见 [TESTING.md](TESTING.md)，本地模型持续转写的资源采样见 [RESOURCE-USAGE.md](RESOURCE-USAGE.md)。

- 豆包引擎：一条连接最长能保持多久没有测到上限（实际每段讲话一条连接，最长跑过 40 秒）；连续几小时的课堂、两路同时长时间识别、真实断网（而不是模拟掐断）都还没有实测。一句话一直不停顿时，约 20 秒才定稿一次，这期间只有预览。
- 豆包引擎的「精修全文」只用文件回放测过，最长一次 269 秒；真实课堂长度（几十段上传）、上传中途断网、单段大小的上限都还没有实测。
- `lstf` 判断听流是否在运行，靠的是状态文件里的进程号是否还活着。听流崩溃后进程号恰好被别的进程占用时，`lstf status` 会误报「正在运行」，直到听流再次启动；读取转写不受影响。
- 下面几条关于切段和 8 秒上限的说明只针对本地模型。

- 远场收音（电脑放在讲台远处、内置麦克风）时讲话只比底噪高约 10 dB，错字仍明显多于近距离收音。最有效的办法是让麦克风靠近说话人或用外接麦克风；调高系统输入音量对识别帮助不大，因为噪声会被同样放大。
- 一直不停顿超过 8 秒时仍会被迫切开，切点可能落在字中间；高精度档或事后精修会把它和相邻片段合起来重识别。
- 准确率数据来自合成语音加底噪，多人插话、背景音乐、口音等真实会议情况还需要实测。
- 区分「App / 电脑声音」和「麦克风」来源，尚不区分会议中不同讲话人。
- 全局模式会录下电脑上的一切声音：提示音、背景音乐、别的窗口里的视频都会进来。豆包引擎下，有声音就会上传并计费，不只是有人说话的时候；只关心一个 App 时用「指定 App」更省。
- 麦克风开启且使用扬声器外放时，重复录入的 App 声音按文字去掉；你和对方同时说话的那几句里，偶尔仍可能混进对方的几个字。戴耳机最干净。
- 默认输入设备取自 macOS；暂未提供独立麦克风设备选择器。
- App 退出、设备切换、休眠或权限变更可能中断采集，需要重新开始。
- 连续长会话、双路同时讲话、多种会议软件与受保护媒体需要进一步实测。
- 测试片段的延迟不能代表任何负载下都保证 10 秒以内。

参考：[Apple ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit)、[MLX Audio](https://github.com/Blaizzy/mlx-audio)、[DeepSeek 模型接口](https://api-docs.deepseek.com/quick_start/pricing/)。

## 后续整理设计

计划改为「新增转写 + 约 20–40 秒重叠原文」的增量整理：前文定稿保持稳定，只重写末尾与重叠原文对应的段落，用片段 ID 和时间戳防止漏段、重复；录音结束后提供可选全文校对。当前 0.2.1 仍按已有全文快照整理，自动模式默认关闭。

## AI 回答的 Markdown 显示

0.3.0 开始，右侧 AI 回答支持标题、加粗、斜体、删除线、行内代码、有序/无序和嵌套列表、引用、表格、分隔线、链接与代码块。长代码和宽表格可在问答栏内横向滚动，文字可以选择。

「复制回答」复制原始 Markdown；「复制代码」只复制代码正文。历史问答自动使用新的显示方式，保存与导出仍保留原文。基于系统 Markdown 解析和原生视图，不运行回答中的 HTML 或代码，也不自动加载远程图片。当前不提供 LaTeX、Mermaid 或代码语法高亮。

## 手动上传图片与看图问答

0.4.0 增加本地图片上传，不自动截屏。

- 右侧输入框上方「添加图片」用于当前提问；整理稿上方「添加参考图片」用于整理。两组选图独立。
- 0.4.1 起，点击右侧问答输入框后按 `⌘V` 可粘贴截图或复制的图片；也支持在 Finder 复制图片文件后粘贴。截图快捷键 `⌃⌘⇧4` 可直接把选区放进剪贴板。粘贴后显示缩略图，保留已输入的问题；普通文字按光标位置粘贴。`Shift-Return` 换行，`Return` 或 `⌘Return` 发送。粘贴的图片也能通过整理稿的「会话图片」选作参考。
- 可以一次多选，每次请求最多 6 张。支持 PNG、JPEG、HEIC、GIF、WebP 等系统可解码图片；GIF 使用首帧。单个原文件限 32 MB，导入时在本机转为 JPEG、最长边缩至 2560 像素并移除原文件元数据。密集小字建议先裁剪。
- 点击缩略图可预览；点击 × 只取消本次使用，图片仍保留在会话图库中。通过「会话图片」可重新选择，不必再次导入。
- 添加图片本身不联网。发起问题或整理时，将当前选中的图片与对应文字发送给已配置的 LLM API。选图会保持到手动取消；历史会话恢复最近问答和整理稿的选图，界面会显示当前选择。不会隐式发送未选中的历史图片。
- 没有录音也可以看图提问或整理图片资料。只添加图片、不输入问题时，发送按钮会使用默认的图片说明请求。
- 整理时区分发言和图片资料：转写引用时间戳，图片引用「图片N」；图片独有信息单列“图片补充（非发言记录）”。图片不能证明会议中已说过这些话。
- 自动整理开启时，会在后续整理中继续使用已选参考图片；更换图片选择后会再次更新。
- 图片副本保存在 `~/Library/Application Support/ListenFlow/Images/<会话ID>/`。会话记录保存图片引用，旧版记录可继续读取。
- 导出 Markdown 时，会在旁边创建同名 `.images` 文件夹并复制会话图片；分享导出文件时应同时带上该文件夹。

需要配置支持视觉输入的模型，默认 DeepSeek Flash 已完成真实图片 API 测试。更换服务后如出现不兼容错误，请确认该模型支持 chat/completions 的 image_url 内容块。
